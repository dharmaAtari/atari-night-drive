# Project Structure

Atari Night Drive is a 2D game built with [Phaser](https://docs.phaser.io/) (JavaScript).
It follows an **ECS (Entity-Component-System)** architecture so that gameplay logic stays
decoupled from input handling — letting us support multiple input systems (currently
touch and keyboard) without duplicating game code.

## Directory Layout

```
.
├── index.html          # page that hosts the canvas and loads src/main.js
├── src/
│   ├── entities/       # Entity base class + entity factories
│   ├── components/     # plain data containers attached to entities
│   ├── systems/        # logic that operates on components each frame
│   ├── scenes/         # BaseScene loop, keys.js, one file per screen
│   ├── config.js       # loads + parses bin/config.xml
│   └── main.js         # Phaser bootstrap + game loop entry point
├── bin/
│   ├── config.xml      # runtime settings (screen size, fps, sound mapping, ...)
│   ├── lib/            # vendored Phaser runtime (generated by `make build`)
│   └── assets/
│       ├── sounds/     # audio files (engine, ui, ambience)
│       └── sprites/
│           └── animations/  # spritesheets / animation frames
└── makefile            # build, run and packaging targets
```

## `src/`

### `entities/`
An entity is just an id with a set of components — no behaviour of its own.
`Entity.js` is the base class holding that bag: `add()` attaches components
(keyed automatically off each component's `type`), `get()` reads one back, and
`has()` is what systems filter on.

```js
const startButton = new Entity('menu.startButton')
  .add(Transform({ x: 320, y: 240 }))
  .add(Shape({ kind: ShapeKind.RECTANGLE, width: 200, height: 28 }))
  .add(Text({ content: 'START', align: TextAlign.CENTER }));
```

The rest of this folder holds the factories that assemble the recurring ones
(e.g. `player.js`, `enemyCar.js`, `roadSegment.js`), each returning an entity
composed of the components it needs. Prefer a factory over subclassing `Entity`
— an entity that grows methods stops being an entity.

### `components/`
Pure data, no logic. Each module exports a factory returning a plain object plus
the key it is stored under; `index.js` re-exports all of them and collects the
keys in `ComponentType`. Components are what systems query against, so keep them
small and single-purpose.

| component | holds |
| --- | --- |
| `Transform` | position, rotation, scale, render depth |
| `Shape` | a drawable primitive — rectangle, circle, line, polygon — with fill and stroke |
| `Text` | a string plus its font style |
| `Collision` | collider bounds, layer/mask bits, and the contacts found this frame |
| `UserInput` | the player's intent — `up`/`down`/`action`, each with held and edge state |

`Shape` uses numeric `0xRRGGBB` colours and `Text` uses CSS colour strings,
because that is what Phaser's Graphics and Text APIs respectively take — the
components match what their renderer consumes rather than converting twice.

`UserInput` is the one to understand first: it is the component the ECS split
exists for. The entire input surface is three buttons — `up` and `down` navigate
menus, and `action` is the only one gameplay reads. See the note under
`systems/` below.

### `systems/`
All behaviour lives here. Each system iterates over the entities that have the
components it cares about and updates them once per frame. Examples:

Built so far:

- `RenderSystem` — turns `Transform` + `Shape`/`Text` into Phaser game objects.
  Creates each object once and syncs it every frame after that, so a shape's
  `kind` is fixed at creation while position, colours and text content are live.
- `KeyboardInputSystem` — the only file that knows a keyboard exists. Writes the
  scene's `UserInput`, deriving `justDown`/`justUp` from the previous frame
  rather than Phaser's `JustDown`, which is consumed when read. Held keys are
  tracked in one page-level listener rather than per-scene Phaser `Key` objects,
  which start each scene believing nothing is pressed.
- `UserInputSystem` — copies the scene's `UserInput` onto every entity that has
  one, field by field. Sharing the button objects instead would let one entity
  consume an edge for all of them.

Still to write: `MovementSystem`, `CollisionSystem`, `AudioSystem`, and
`TouchInputSystem`.

Input is the main reason for the ECS split: each input system writes to the same
`Input` component, so gameplay systems never need to know whether the player is
on a keyboard or a touchscreen. Adding a new input method (gamepad, tilt) means
adding one system, not touching gameplay code.

### `scenes/`
Phaser scenes — the screens the game moves between (menu, gameplay, game over).
A scene owns the entity set that exists while it is active and drives the systems
each frame; it is the seam between Phaser's lifecycle and the ECS.

`BaseScene` holds that loop so no screen has to rebuild it. Every scene gets an
entity list, one authoritative `UserInput`, and the two functions the game runs
on:

```
update()   KeyboardInputSystem  device keys      -> scene UserInput
           UserInputSystem      scene UserInput  -> each entity's UserInput
           updateEntities()     scene logic, reading input off its entities
render()   RenderSystem         Transform + Shape/Text -> Phaser game objects
```

The order matters: input is read once per frame and fanned out before any scene
logic runs, and rendering happens last, on the transforms that logic just wrote.
Subclasses fill in `build()` and `updateEntities()` rather than overriding
`update()`, so they cannot run logic before input is current or after the frame
is drawn.

One gotcha it exists to avoid: the scene's input component is `this.userInput`.
`this.input` is Phaser's own input plugin, and assigning over it breaks the
scene.

`MenuScene` is the entry point — PLAY and QUIT labels plus a selection box,
three entities in total. Only the box carries `UserInput`, since it is the only
thing the player moves; `updateEntities` reads `up`/`down` off it and writes the
chosen row's position into the box's own `Transform`. Each row pairs its entity
with what activating it does, and those handlers live on the scene rather than
the entity — entities stay data, and the scene is what can change scenes.

`GameScene` is where the driving will go. It is a placeholder today, and PLAY
starts it.

Scene keys live in `keys.js` rather than on the scene classes, so the menu can
start the game and the game can return to the menu without the two importing
each other.

**Handing over while a button is held.** `action` both activates PLAY and is the
button gameplay reads, so it is usually still down when the next scene starts.
Two things stop that from registering as a fresh press in the new scene:
physical key state is tracked once for the page rather than per scene (see
`KeyboardInputSystem`), and `BaseScene.create()` primes the input — adopting
whatever is held as already-down instead of reporting an edge for it.

### `config.js`
Fetches and parses `bin/config.xml` into a plain object before the game boots,
so every other module reads settings from one place.

### `main.js`
Loads the config, then constructs the `Phaser.Game` from it — display size,
scale mode, target fps and background colour all come from `config.xml`.

## `bin/`

The runtime/distributable side of the project — everything the game loads at run time.

### `config.xml`
Externalises settings so they can be changed without a rebuild:

- **Display** — screen width/height, scale mode, fullscreen
- **Performance** — target fps
- **Audio mapping** — logical sound name → file, e.g. `enginesound: vroom.mp3`
- Any other tunable game settings

Systems read values from this config rather than hardcoding them.

### `lib/`
The Phaser runtime, copied out of `node_modules/` by `make build`. It is
generated (and git-ignored) so the game can be served as plain static files with
no bundler in the loop — `src/` uses native ES modules.

### `assets/`
- `sounds/` — audio files referenced by the config's sound mapping
- `sprites/` — static sprite images
- `sprites/animations/` — spritesheets and animation frame sets

## `makefile`
Top-level entry point for common tasks, so the project can be driven with plain
`make` commands:

| target | what it does |
| --- | --- |
| `make deps` | `npm install` (fetches Phaser) |
| `make build` | vendors the Phaser runtime into `bin/lib/` |
| `make run` (or `make serve`) | builds, then serves the game at `http://localhost:8000/` |
| `make package` | writes a self-contained tree to `dist/` |
| `make clean` | removes `bin/lib/` and `dist/` |

Override the port with `make run PORT=9000`.
